# netweir v0.1 design

Status: draft, October 2026
Author: James Conway

## What v0.1 is

netweir is a web scraping library with a Rust engine and a Python API. Version 0.1 covers three things: fetching pages so they look like they came from a real browser, parsing them fast, and crawling whole sites without losing work when something breaks.

A browser driver, a stealth layer for JavaScript-heavy sites and a hosted service all come later. v0.1 leaves room for each of them but builds none of them.

The goal for v0.1 is to be the fastest Python crawler you can install, measured in public, in CI, against Scrapy, Scrapling and a hand-rolled httpx + selectolax script.

## Scope

In v0.1:

- HTTP/1.1 and HTTP/2 fetching with Chrome, Firefox and Safari TLS and HTTP/2 fingerprints
- An HTML parser with CSS selectors, XPath 1.0 and a Beautiful Soup style `find` / `find_all`
- A crawl engine: priority queue, per-domain concurrency, dedup, robots.txt, adaptive throttling
- Declarative spiders that run with no Python per page, and ordinary spiders with an async `parse`
- Self-healing: tracked selectors that survive markup changes, block detection and recovery, crash-safe resume, and an optional LLM selector repair plugin
- Exporters for JSONL, CSV and Parquet
- A `netweir` command line tool
- Wheels for macOS, Linux and Windows on arm64 and x86_64, Python 3.10 and up, plus free-threaded 3.14t

Not in v0.1:

- HTTP/3. No Rust stack can copy a browser's QUIC fingerprint yet.
- A browser driver. Planned for v0.2, over CDP.
- Multi-process workers. The engine is designed for them; they ship in v0.2.
- Fingerprint rotation services, residential proxies and CAPTCHA handling. These belong to the hosted service and never go in this repo.
- Login automation.
- Drop-in compatibility with Scrapy or Beautiful Soup. The concepts carry over; the API is new.

## Architecture

Python runs the crawl loop. Rust does the work.

```
Python (user API)                         Rust engine (one per crawl, own tokio runtime)
─────────────────                         ────────────────────────────────────────────
Spider class / declarative rules  ──────► Frontier: priority queue, per-domain slots,
async for batch in engine.results():       dedup (fingerprint), robots.txt + TDMRep,
   custom callbacks (if any)                adaptive per-domain delay
   yield items / requests  ─────────────►  Transport (wreq): profiles, cookies, proxies
Pipelines / exporters (Python or           Block classifier → retry / rotate / back off
   built-in Rust: JSONL, CSV, Parquet)     Parser + CSS + XPath (rayon pool)
                                           Declarative extractor (no Python)
                                           Checkpoint store (SQLite, WAL)
```

The reasoning: on a single site, crawl speed is set by the network and by politeness. Across many sites, it's set by CPU time per page, and most of that goes on parsing, on framework overhead and on running user code. Parsing and framework work move to Rust threads that never hold the GIL. User code only runs when the spider has a custom callback, and declarative spiders don't.

Python and Rust meet at one place, a bridge module in `netweir-py` built on pyo3-async-runtimes. Python asks for completed work in batches, so the event loop wakes once per batch, not once per request. If pyo3-async-runtimes turns out to be the bottleneck, the bridge is the only file that changes.

The crawl state on disk does not depend on Python, so a later version can run N Python worker processes against one engine for spiders with heavy custom callbacks.

### Sessions

A session is a browser profile, a proxy and a cookie jar, bound together. They are always swapped together, never one at a time. Most bot detection today catches requests whose layers disagree with each other (a Chrome TLS handshake with a Firefox user agent, a US proxy with a German `Accept-Language`), not any one signal on its own.

## Components

### netweir-dom

No Python and no network, so it can be tested and benchmarked alone.

- lexbor (Apache-2.0, C) parses the page and holds the tree. It is a git submodule pinned to a release tag, compiled by `build.rs` with the `cc` crate, so a build needs a C compiler and nothing else.
- Rust reaches lexbor only through a small C file of accessor functions, never through lexbor's struct layouts, which change between releases.
- lexbor's own selector engine runs CSS queries. `::text` and `::attr(name)` are stripped from the query before matching and applied to the result in Rust.
- XPath 1.0 is written from the spec, plus the `re:test` extension Scrapy users rely on, and walks the lexbor tree through the same accessors.
- encoding_rs and chardetng handle character encodings.

Python sees an `Arc<Document>` and small node handles (document reference plus node pointer). Bulk calls such as `.getall()` return `list[str]` straight from Rust without creating a Python object per node. Parsing and queries release the GIL.

Why lexbor and not html5ever: measured on a 1.4 MB page, html5ever's tokenizer alone took 12.5 ms, while lexbor parsed the whole page in 4.2 ms. Copying lexbor's tree into a Rust arena cost another 2 ms, which lost to selectolax, so the tree stays in lexbor's memory. Running the query and building the strings in Rust is what puts netweir ahead of selectolax, which uses the same parser.

Some inputs are slow for any HTML5 parser: thousands of unclosed `<div>`s make parsing quadratic in nesting depth (400 KB took 5 s in lexbor and longer in html5ever). Browsers cap the depth; lexbor doesn't. So parsing is chunked, and the crawler parses with a time budget and gives up on pages that blow it.

The parser follows the HTML5 spec, so it inserts `<tbody>` the way browsers do. Selectors copied from browser devtools work. Some written for lxml won't, and the docs say so.

### netweir-core

**Transport.** wreq, btls and http2, pinned to exact versions, unmodified, behind a `Transport` trait that netweir owns. wreq-util is not used: its licence has changed four times, including to GPL-3.0. Browser profiles are netweir's own, captured from real browsers by `tools/capture` and stored as data in `profiles/`. If the single maintainer of wreq stops, the first replacement is our own HTTP/2 layer on Cloudflare's `boring` crate; the trait means nothing else changes.

**Frontier.** A priority queue with per-domain slots, global and per-domain concurrency limits, request fingerprinting for dedup, and robots.txt and TDMRep checks. URLs are canonicalised before fingerprinting: query keys sorted, fragments dropped, known tracking parameters removed.

**Throttle.** Each domain starts at a configured delay. On each response, the target delay is latency divided by target concurrency, and the next delay is the mean of the current delay and the target. Only successful responses can lower the delay. Blocks and 429s raise it. The delay stays between the configured minimum and maximum.

**Block classifier.** See Errors and recovery.

**Declarative extractor.** Compiles `Item` fields and `rules` into a plan once per spider, then runs it on each page in Rust.

**Checkpoint store.** One SQLite file per crawl, WAL mode, bundled with the wheel. It holds the pending queue, seen fingerprints, completed requests and tracked selector fingerprints. More in Crash safety.

### netweir-py

Thin PyO3 bindings and the async bridge. No logic lives here that could live in core.

### python/netweir

The user-facing package: `Spider`, `Item`, `Settings`, `Follow`, pipelines, exporters, the CLI and the LLM repair plugin. Rust logs are routed into Python's `logging`.

## Python API

### One-off fetch and parse

```python
import netweir as nw

page = nw.get("https://books.toscrape.com/", profile="chrome")

page.css("h1::text").get()                    # "All products"
page.css(".price_color::text").getall()       # ["£51.77", "£53.74", ...]
page.xpath("//article//h3/a/@title").getall()
page.find("li", class_="next")                # Beautiful Soup style, same node type
page.status, page.headers, page.blocked       # blocked: None | "cloudflare" | "datadome" ...

async with nw.Client(profile="firefox", proxy="http://...") as client:
    pages = await client.get_many(urls)
```

A page is a response and a parsed document in one object. `css`, `xpath` and `find` return the same node type, so they can be mixed. `nw.get` is the only synchronous entry point; everything else is async.

### Declarative spider

```python
class Book(nw.Item):
    title = nw.css("h1::text")
    price = nw.css(".price_color::text", re=r"[\d.]+", into=float)
    upc   = nw.xpath("//th[.='UPC']/following-sibling::td/text()")

class Books(nw.Spider):
    start_urls = ["https://books.toscrape.com/"]
    rules = [
        nw.Follow("li.next a"),
        nw.Follow("article.product_pod h3 a", extract=Book),
    ]
```

```
$ netweir crawl books.py -o books.jsonl
```

No Python runs per page. Python only sees finished items.

### Spider with a callback

```python
class Quotes(nw.Spider):
    start_urls = ["https://quotes.toscrape.com/"]

    async def parse(self, page):
        for q in page.css("div.quote"):
            yield {
                "text": q.css(".text::text").get(),
                "author": q.css(".author::text").get(),
                "tags": q.css(".tag::text").getall(),
            }
        if nxt := page.css("li.next a::attr(href)").get():
            yield page.follow(nxt)
```

`rules` and `parse` can be combined: rules handle link following in Rust, and `parse` runs only on the pages that need it.

### Tracked selectors

```python
price = page.css(".price_color", track="price")
price.relocated     # True if the original selector missed and the element was found by similarity
price.score         # similarity of the match, 0 to 1
```

`track=` also works on `nw.css(...)` and `nw.xpath(...)` fields.

When a tracked selector matches, netweir stores a fingerprint of the element: tag, text, attributes, the tag path of its ancestors, its siblings' tags, and its parent's tag, attributes and text. Fingerprints are keyed by domain and track name and stored in the checkpoint file, or in `~/.netweir/tracks.db` outside a crawl.

When the selector later finds nothing, every element of the same tag family is scored against the fingerprint. The weights are netweir's own and are tuned on a corpus of real before-and-after page pairs kept in `tests/fixtures/redesigns/`. The best match is returned if its score clears `Settings.track_threshold` (default 0.75). Below that, the result is empty and a warning is logged. Every relocation is logged with its score.

The optional `nw.repair.llm(model=...)` plugin takes a failed tracked selector and the new page, and proposes a replacement selector. It never applies a fix on its own; it writes proposals to the crawl report for the user to accept.

### Settings, pipelines and output

```python
class Books(nw.Spider):
    settings = nw.Settings(
        concurrency=256, per_domain=8,
        profile="chrome", obey_robots=True,
        checkpoint="crawls/books",
    )
    pipelines = [drop_out_of_stock, nw.export.jsonl("books.jsonl")]

async def drop_out_of_stock(item):
    return item if "In stock" in item["stock"] else None
```

A pipeline is an async function that returns the item, a changed item, or `None` to drop it. The built-in exporters run in Rust.

### Defaults

netweir obeys robots.txt and TDMRep, and throttles per domain, out of the box. The default user agent is the profile's real browser user agent. Turning robots.txt off is an explicit setting (`obey_robots=False`) that logs a warning once per crawl. HTTP 402 is always surfaced, never retried.

## Errors and recovery

### Outcomes

Rust classifies every fetch into one outcome before Python sees it.

| Outcome | Example | Default handling |
|---|---|---|
| `ok` | 200 with content | parse, extract, follow |
| `blocked(vendor, kind)` | `cf-mitigated: challenge`, DataDome 403, Kasada 429, AWS WAF 202 | new session, retry |
| `throttled` | 429 or 503 with `Retry-After` | wait, slow the domain |
| `payment_required` | 402 with a price header | never retried, reported with the price |
| `http_error(status)` | 404, 500 | 5xx retried with backoff, 4xx recorded |
| `network_error(kind)` | timeout, DNS, TLS, reset | retried with backoff |

In a crawl these are data: they show up in stats, the `on_block` hook and the failed-requests log. `nw.get` raises `nw.Blocked` on a block unless called with `raise_on_block=False`.

### Block classifier

Checks run in order of reliability: headers, then cookies, then body markers, then status code. Vendor signatures (Cloudflare, Akamai, DataDome, HUMAN, Kasada, Imperva, AWS WAF) live in one data file shipped with the wheel, so adding a signature is a data change. Each signature has a recorded fixture in the test suite.

### Recovery ladder

Per request, each step only if the last failed:

1. Retry on the same session after exponential backoff with jitter (5xx and network errors).
2. New session: profile, proxy and cookie jar replaced together (blocks).
3. Slow the domain: blocks and 429s count against its throttle.
4. Circuit breaker: if more than 30% of the last 50 requests to a domain were blocked, the domain pauses and one warning is logged.
5. Give up: the request goes to the failed log and `on_block`.

Attempt limits, breaker thresholds and backoff timings are all settings. In v0.2, a step between 4 and 5 escalates to a real browser.

### Crash safety

The checkpoint file is SQLite in WAL mode, which is crash-safe without any code of ours. Requests are stored as plain data with callbacks referenced by name. Nothing is pickled.

After `kill -9`, rerunning the same command resumes the crawl. Delivery is at least once: requests in flight at the crash are fetched again. Every item carries a stable `_id` (a hash of the request fingerprint and the item's position in that page's output) so exporters skip duplicates.

The file records a format version. A newer netweir resumes a checkpoint written by an older one.

### Traps

Canonical URLs before dedup, a maximum depth, a per-domain page limit, and rejection of URLs whose path repeats the same segment group three or more times.

### User code

An exception in a callback or pipeline is logged with the page URL, counted, and the crawl continues. `fail_fast=True` stops on the first one.

## Room for the hosted service

v0.1 doesn't build the hosted service, but a few choices now keep it a plug-in later:

- `Transport` is a trait, so a remote backend can stand in for wreq.
- Request options use the same field names as the common hosted scraping APIs where they overlap (`httpResponseBody`, `geolocation`, `session`), and the request fingerprint includes them, since the same URL fetched two ways is two requests.
- Every response carries a `usage` field the hosted service can fill in for billing.
- Extraction is a separate step from fetching, so it can be priced separately.
- Items, logs and stats leave through one output interface a hosted collector can capture.
- A crawl reports its peak memory.

JA4 (BSD-3) is the only fingerprint the hosted service will compute. JA4H, JA4S, JA4T and JA4X are under the FoxIO License and need a paid licence for commercial use; their code stays out of this repo.

## Testing

**Rust.** `cargo test` on every crate. XPath tests are written from the examples in the XPath 1.0 spec. `cargo-fuzz` targets the parse and query entry points and the XPath parser. Hostile inputs (deep nesting, NUL bytes, random bytes) are in the ordinary test suite.

**Python.** pytest against `maturin develop --uv`.

**No live internet in gating tests.** A local test server stands in for the web: paginated sites, traps, slow and failing pages, and recorded block pages from each vendor.

**Fingerprints.** The test server records the TLS ClientHello and HTTP/2 frames of each request, computes JA4 and the Akamai HTTP/2 string, and compares them with the reference captured from the real browser. A profile that drifts by one extension fails CI.

**Crash recovery.** A crawl against the local server is killed with `kill -9` at random points and resumed. The test asserts no request was lost and every `_id` is unique.

**Live smoke tests.** Nightly, never gating: books.toscrape.com, quotes.toscrape.com and a TLS fingerprint echo service.

**Profile freshness.** A weekly job opens an issue when a new stable Chrome, Firefox or Safari ships.

## Benchmarks

| Benchmark | Compared with | Measure |
|---|---|---|
| Parse + query, 1 MB and 10 MB pages | lxml, selectolax, Beautiful Soup, parsel | ms per page. CI fails if selectolax is faster |
| Crawl, 10,000 pages across 100 domains at 50 ms simulated latency | Scrapy, Scrapling's spider, an httpx + selectolax script | pages/sec, CPU-seconds per page, peak RSS |

Benchmarks run in CI. A pull request fails if it's more than 10% slower than a baseline run in the same job. Results are published in the README.

## Risks

| Risk | What we do |
|---|---|
| wreq has one maintainer | Pinned, behind our trait. Replacement path: own HTTP/2 on `boring`. |
| The lead over selectolax is small (2–7%) because both use lexbor | The benchmark gates CI. The lead comes from batching in Rust, so it grows with the work done per page. |
| Hostile pages that are slow to parse | Chunked parsing with a time budget. |
| Browser profiles go stale every Chrome release | Captured by our own tool, checked weekly. |
| BoringSSL builds on Windows and musl | Native MSVC runners, not cross-compiling. Build times measured in the first CI run. |
| Tracked selector weights are guesswork | Tuned against a corpus of real redesigns, score exposed to the user. |
| Free-threaded Python and pyo3-async-runtimes | 3.14t in the test matrix from day one. |
